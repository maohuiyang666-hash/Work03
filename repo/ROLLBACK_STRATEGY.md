# 生产环境部署与回滚策略

为了确保游戏的生产环境稳定性，我们采用了以下工程化部署与回滚策略：

## 1. 自动化 CI/CD 与构建验证
- **CI 质量门禁**：在 `main` 分支发生推送时，GitHub Actions 会自动触发部署工作流。部署前首先运行 `npm run lint` 进行代码质量检查。
- **构建产物验证**：构建完成后，自动运行 `scripts/check-build.mjs`。该脚本会检查产物完整性（如 `dist`、`index.html` 是否存在）、主要 JS/CSS 资源是否存在、资源大小是否超出阈值，以及排查可能导致 404 的错误绝对路径风险。
- **验证前置**：只有当 CI 质量检查和构建产物验证均通过后，才会执行上传 artifact 和 GitHub Pages 部署步骤。

## 2. 部署失败处理
- **原子性发布**：部署过程基于 GitHub Actions 的 `actions/deploy-pages` 进行。如果在构建、验证或上传产物等任何阶段发生失败，整个流程将被终止，不会触发发布操作，从而**不覆盖现有的线上版本**。

## 3. 回滚策略
- **Artifact 保留机制**：每次成功构建都会生成一个对应版本的 Build Artifact，保存在 GitHub Actions 的运行记录中。
- **快速回滚**：如果发现线上版本出现严重问题，开发者可以前往 GitHub Actions 页面，找到最近一次已知稳定的构建记录（Artifact），重新运行部署（Re-run jobs）或手动下载 Artifact 并部署，从而实现秒级回滚。
- **代码回滚**：通过 Git 提交流程，使用 `git revert` 撤销产生问题的 commit，推送至 `main` 分支。由于我们已经配置了自动化的 CI/CD 流程，提交修复后将自动走完完整的构建与部署流程，快速恢复线上服务。
